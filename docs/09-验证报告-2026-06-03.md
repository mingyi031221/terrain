## 1. 任务一：修地图山头位置（只改 `layout.ts` 位置计算）

### 1.1 做了什么
重写 `scatterLayout`（`src/features/terrain-map/layout.ts`），**只产出 x/y 坐标**，
渲染、连线虚线、旗子、当前节点小猫一概没动（它们都读这套 x/y，自动跟随）。

1. **地面带**：节点中心 y 限制在画布高度的 **45%–80%**（拥挤时放宽到 **42%–84%**）。
   上方留天空、下方留标签空间，所有山坐在草地上，不再飘天上。
2. **不重叠**：先按依赖层级铺 x、在带内分散 y 并加确定性抖动；再做 **relaxation**——
   两两按"较小穿透轴"把过近的推开，**间距把标签胶囊宽度算进去**
   （`footprint = max(山宽, 标签宽)`，标签宽按 CSS `max-width:160px` 封顶），
   配一个弱"列回弹"保持左→右流向，每轮夹回地面带与左右留白。
3. **稳定**：以 `topic + 节点id` 为种子，纯函数；同一张地图刷新坐标完全一致。
4. **依赖虚线 / 旗子 / 当前小猫**：未改动。

### 1.2 自己定的决策与原因
- **地面带取 45%–80%（拥挤放宽 42%–84%）**：渲染里山的锚点是 `translate(-50%,-52%)`，
  节点点位≈山体下半/山脚，45%–80% 能保证山顶上方有天空、标签下方有空间。
  你给的参考是 42%–82%；我把"拥挤情况"的下沿放到 84%，是为了让 ≥7 座山或某层 ≥3 座时，
  relaxation 有足够纵向空间把它们分开（否则物理上塞不下）。**这是我自行微调的一处，已标注。**
- **拥挤判定 = 节点≥7 或某层≥3**：普通地图用更紧凑自然的窄带；只有挤时才放宽，避免小图显得松散。
- **标签宽封顶 160**：CSS 标签 `max-width:160px` + 省略号，所以按 160 估算最准，避免高估间距把山推太散。
- **relaxation 而非纯网格**：网格能保证不重叠但呆板；relaxation + 弱列回弹既散得自然、又保住左→右依赖可读性。
- **种子含 topic**：不同主题的地图散布不同、同主题刷新不变——既稳定又不千篇一律。

### 1.3 验证方法

+ 同一套 `footprint`）逐张检查：每个节点是否在地面带内、任意两点框是否重叠。

## 2. 任务二：可选「小测」（仿 node-detail 链路）

### 2.1 做了什么（链路逐环对齐 detail）
prompt → schema → service → route → 前端 fetch → reducer → 面板，全程过 Zod 校验、
像 map/detail 一样做内存缓存。**点击「测一下」才按需生成，绝不自动生成。**

新增/改动文件：
- `server/prompts/quiz.v1.md`（温柔语气规则，核心，见 §2.3）
- `src/types/terrain.ts`：`QuizQuestionSchema` / `TerrainQuizSchema`
- `server/schemas/quiz.ts`、`server/services/quiz-generator.ts`(+test)
- `server/routes/terrain-quiz.ts`(+test)、`server/index.ts` 注册、`server/lib/caches.ts` 加 `quizCache`
- `src/lib/api.ts` `fetchQuiz`、`src/store/quiz-reducer.ts`(+test)
- `src/features/node-detail/QuizPanel.tsx`(+test)、挂进 `NodeDetailPanel`、`App.tsx` 接线、`global.css` 样式

### 2.2 schema 约束
题目 2–3 道，`type='choice'|'truefalse'`、`question`、`options`、`answerIndex`、`explanation`；
`superRefine` 校验：`answerIndex` 在范围内、判断题恰好 2 项（`["对","错"]`）、单选 ≥3 项。
失败重试一次、校验 `nodeId` 回填一致，与 detail 完全同构。

### 2.3 语气规则落实（写进 quiz.v1.md + 前端共同保证）
- 框成「看看你 get 到了没」、可「先不测了」跳过，**绝不出现"考试/检验/测验你学会没"**。
- 答错走**解释式**反馈「这题容易混，其实是…」，**不是**红叉打击；UI 上正确项绿色 ✓、
  选错项只标"你选的"（柔和琥珀色，**无红 ✗**）。
- 计分由前端温柔显示「你 get 到了 X/N ✨」+ 鼓励语，LLM 不负责打分。
- 答错时前端用当前节点标题温柔指回：「这块对应「X」那座，回头再扫一眼？」
- 测理解优先情景/判断题，少问"X 的定义是什么"。
- 节点原有「挂个钩子」反思小语**未改动**，小测是另加的。

### 2.4 真实调用样题（给你人工验收语气用）
`POST /api/terrain/quiz`，body `{"topic":"Docker","nodeId":"node-2","nodeTitle":"镜像怎么来的"}`，
HTTP 200，原样返回：

**Q1（判断）** 镜像都是官方直接提供的，用户不能自己创建。
- 选项：对 / 错 ｜ 正确答案：**错**（index 1）
- 反馈：「错，你可以用 Dockerfile 自己构建镜像，就像搭积木一样。」

**Q2（单选）** 下面哪种方式最接近创建镜像的原理？
- 选项：A 像下载软件一样直接从网上获取 / B 像做蛋糕一样，按照配方一步步来 / C 像复制文件一样直接拷贝
- 正确答案：**B**（index 1）
- 反馈：「这题容易混，其实镜像更像是按步骤制作的成品，不是直接拿来的。」

**Q3（单选）** 如果我要把一个程序变成镜像，第一步应该做什么？
- 选项：A 直接打包成文件 / B 写一个 Dockerfile 来描述怎么构建 / C 找别人已经做好的镜像
- 正确答案：**B**（index 1）
- 反馈：「对，Dockerfile 就像说明书，告诉 Docker 怎么一步步做出镜像。」

> 语气核对：混了 1 判断 + 2 单选；反馈是解释式（搭积木 / 做蛋糕配方 / 说明书的类比），
> 测的是"理解原理"而非背定义；没有任何考试腔或打击词。符合产品语气规则。

### 2.5 自己定的决策与原因
- **模型复用 `LLM_MODEL_DETAIL`（默认 qwen-turbo）**：你没指定小测专用模型；小测和详情同属轻量生成，
  复用既省配置又一致。若以后想区分，加个 `LLM_MODEL_QUIZ` 即可。
- **"指回对应的山"在前端拼**：节点标题前端最可靠，避免依赖 LLM 把标题填对；LLM 只负责把 explanation 写温柔。
- **小测独立 reducer、按 nodeId 防串台**：切节点/换主题/关详情都会重置，避免显示上一节点的旧题。
- **NodeDetailPanel 的 quiz 相关 props 设为可选带默认**：让既有面板测试无需大改即可通过；App 始终传全。
- **缓存键 = topic+nodeId+nodeTitle**：同一节点重复点「测一下」不重复烧额度（与 map/detail 一致）。
